# FR-28 — Batch-Dokumentationsschärfung und Signatur-Helfer

**Quelle:** [`martinderm/office-intelligence#4`](https://github.com/martinderm/office-intelligence/issues/4)
(Doku­mentationslücken aus realem Batch, 2026-10-15, boku-user-Workspace).
**Status:** in Umsetzung (DOC-P1 läuft).
**Betroffene Skills:** mail-desk (nur Referenzen + ein neues Helferskript).

## Problem

Ein regulärer Standard-Batch (10 Mails, `draft → execute → verify`, 2026-10-15)
musste mehrere bindende Verträge aus dem Quellcode rekonstruieren, weil die
Referenzdokumentation sie nicht beschreibt. Vier Lücken plus Ablagefrage:

## Pakete

### DOC-P1 — Referenz-Dokumentation A–E + `mail_desk_sign_manifest.py`

**A — Review-Korrektur-/Signaturpfad (hoch):** `references/batch-runner.md`
beschreibt den expliziten Schritt „Reviewte Korrekturen anwenden & neu
signieren": Korrekturen kommen per Editor in `data/mail-desk/
batch-manifest.json` (`candidate_count` folgt `len(items)`), die Kanonisierung
ist exakt `payload = dict(config); payload.pop("review", None)`;
`json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",",":"),
allow_nan=False)` → SHA-256
(`core/batch_contract.py:canonical_execute_request_sha256`). Neu signiert wird
mit `approval_receipt = {reviewed_at, reviewed_by,
execute_request_sha256}` (exakt diese drei Keys, `review.state == "approved"`
sonst `review_hash_mismatch`). Hilfsskript `scripts/mail_desk_sign_manifest.py`
(stdlib-only, JSON-Ausgabegrenze wie die bestehenden Harness-CLI-Scripts):
lädt Manifest, aktualisiert `candidate_count=len(items)`, berechnet den Hash,
setzt `review` auf approved + Receipt, prüft sich selbst via
`validate_execute_contract`, schreibt atomar zurück; injizierbare Uhr,
niemals Mailbox-Kontakt.

**B — `verify`-Schritt (hoch):** Batch-SOP um `verify` mit Beispiel-Input
ergänzen: `execute_summary` braucht `mode:"execute"`, `ok:true`,
`status:"completed"`, `recovery_required:false`, ergebnisdoppelte ID-Liste
exakt gleich `verify_scope_ids`, alle Zeilen `success:true`,
`synthesis_candidate` Mapping; Muster → kein `completion_report` und
`synthesis_handoff` bleibt leer (`core/modes/verify.py:
_verified_execute_candidate`). Wiederherstellungspfad: `reconcile` read-only
mit vollständigem Journal → `status:"completed"` + freigegebener Handoff.
**Nachtrag Recovery-Fall** (env 9498/9511): „Target verification failed after
copy" → Diagnose read-only `reconcile` zeigt `folder_verified:true`,
`recovery_state:"needs_local_repair"`; Reparaturmanifest
`data/mail-desk/batch-reconcile.json`
(`{"mode":"reconcile","check_folders":true,"apply_local_repairs":true,
"approval":{"state":"approved","reviewed_at":"…","reviewed_by":"…"}}`, sonst
`approval_required`/`verification_required`); Reparatur ist lokal
(Index/Log/Evidence), idempotent (`repaired_count:0` ohne Drift), nie
Mailbox-Mutation und führt `runner-progress.json` auf `completed`/`repaired`
(`FR-19`, Archiv).

**C — Volltext-Read (mittel):** `references/backends/himalaya.md` dokumentiert
`read` mit `preview_lines` (Manifest-Feld und `--preview-lines`, Default 50);
Volltext = hoher `preview_lines`-Wert.

**D — `catalog_inspect.py`-CWD (niedrig):** `references/cli-operations.md`
nennt die Auflösungsregel: Katalogpfad = `--workspace` (Default `"."`,
aufgelöst gegen das Prozess-CWD) + `memory/references/…`; falscher CWD →
`Catalog file not found.`, Exit 1.

**E — Ablage-Norm (niedrig):** Norm in `batch-runner.md`: was nach
`data/mail-desk/archive/YYYY-Www/` wandert (Recovery-Journal-Kopie) und was im
Workspace-Root bleibt (`batch-recovery-journal.json` selbst,
`data/mail-desk/batch-manifest.json`, Globale Synthese liegt an den
Handoff-Zielen `memory/references/{projects,topics}/…`).

**Size-Gate:** `MAX_WORDS` des Slim-Guards wird mit dokumentierter
Testkorrektur (Testkorrektur-Runde, Begründung im Test-Docstring + Ledger)
angehoben; eigentliche Wortzahl wird im Lauf gemessen.

**Verifikation:** neue Fokus-Tests grün, Mail-Desk-Gesamtsuite grün,
Docs-Guards grün, compileall, `git diff --check`.
